# Estao Desktop

The replacement desktop project lives entirely here. Core, OAuth sign-in, and Harness Hub credential discovery are shared with the previous app; no Zarpa UI assembly is loaded.

- `ProviderOverlay.cs`: the original rounded, inline taskbar pill with native provider logos (no painted provider names), grip and separators. Percentage, donut and reset are fixed, regardless of legacy overlay display options. Names remain available to accessibility tools. Drag its grip to move; hover or click a provider for details. It follows Windows light/dark personalization and live preference changes, independently of the web windows.
- `TrayApplicationContext.cs`: native tray menu, refresh scheduling, accounts, pacing notifications, and on-demand web window lifetime.
- `DesktopWindow.cs`: Shofia.WebHost custom-chrome windows hosting embedded React assets, without a backend/server. Settings uses the template's frontend title bar and shared minimize/maximize/close controls. The popover has no title bar or branding; its settings button sits at the right of the provider tabs. Closing either window disposes its WebView2 control.
- `Frontend/`: settings and popover. Provider credentials are write-only to the bridge; stored secrets are never returned to JavaScript. An empty credential field keeps the stored value; removal is explicit.
- Provider cards show **Disabled** when disabled, otherwise **Signed in** or **Not signed in** (warning color). Expanding a signed-in provider shows a sign-out action; expanding a signed-out provider shows only its sign-in fields. Sign-in saves that provider immediately, verifies the account even if disabled, and refreshes only that provider's usage; other providers' cached authentication and usage remain unchanged. Completed sign-in/sign-out banners are hidden; progress and errors remain visible. GitHub device codes have an adjacent copy icon, with Open GitHub and Cancel sign-in on one row. Global Settings Save/Discard is not needed for authentication. Existing pacing and provider preferences are preserved.
- Codex sign-in runs `codex app-server` hidden, opens its ChatGPT authorization URL in the default browser, and waits for the matching `account/login/completed` notification. It targets the saved active Codex profile, refreshes usage automatically, and stops the server on success, error, cancellation, Settings close, or a five-minute timeout. A recent Codex CLI supporting browser login is required; credentials remain managed by Codex. Claude retains its CLI terminal sign-in.
- Settings checks existing Codex authentication separately from usage through `account/read` (without requesting token refresh). Other providers verify available credentials with their usage endpoints. Checks include disabled providers and are cached while Settings is open; reopen Settings to detect a login completed externally. Codex sign-out uses `account/logout` for the active profile (also signing out that CLI profile); Claude sign-out clears the CLI OAuth credential consumed by Estao. Other providers clear only their Estao-held keys, accounts, cookies and OAuth tokens. No unrelated provider credentials are removed. A failed network check is shown as unknown, not as signed out. Temporary Codex processes stop after checking, with no background account probe kept alive.
- **Settings → Appearance**: three light themes (Pearl, Ocean, Lavender) and three dark themes (Midnight, Graphite, Aurora). Preview immediately, then Save or Discard. Both web windows share the saved theme; the native overlay is unaffected.
- **Settings → General → Language**: system language, English, Spanish or French. Save updates native and web text together. See [LOCALIZATION.md](LOCALIZATION.md) for message codes, catalogs, branding and adding languages.
- **Settings → Harness Hub**: browse global/user skills across Codex, Claude Code, GitHub Copilot CLI, and OpenCode, and install HMY library skills directly. Only detected tools are shown. The repository button opens GitHub in the default browser.

To add a theme, add an entry to [`Frontend/src/themes/themes.json`](Frontend/src/themes/themes.json). This single catalog drives the picker, CSS color tokens, native validation, and startup appearance. See [`Frontend/src/themes/README.md`](Frontend/src/themes/README.md) for the color contract and checks.

`dotnet run --project src/Hmy.Estao.Desktop -- --settings` opens settings. Without the flag only the native tray and enabled overlay start. Building automatically installs and bundles the frontend; Node.js is a build-time requirement only.

## Compatibility

Uses the existing config path, `HMY_ESTAO_CONFIG`, DPAPI cookie/OAuth stores, usage history, and provider accounts. The existing `theme` field stores the web theme ID; the former `Graphite` name maps to Graphite, and unsupported names fall back to Pearl. Legacy backdrop settings, overlay display options, provider alert rules, and Harness Hub sections are retained but ignored by this UI.

## Harness Hub

The Hub is a Settings page, after Usage alerts. It reuses `Core/Harnesses/Installer`, not the historical marketplace/installer services. Opening the Hub checks tools, scans local skill metadata, and verifies GitHub access; it does not install anything. Detection checks PATH and common npm, Bun, local-bin, OpenCode, and WinGet locations. Reopen Settings to start fresh discovery. No harness executable or repository script is run.

**Installed** combines discovered skills from detected tools' personal and compatible/shared roots, including skills installed outside Estao. **HMY** lists only items curated in the repository-root `hub-manifest.json`: skills, instructions and other files. **Other** lists uncurated repository skills and local-only skills, not arbitrary repository files. Search, tool/status, category and type filters share one inventory. Descriptions and category labels use the selected UI language, then the catalog default language. Checked tool logos indicate discovered skills; muted logos indicate missing skills and warnings indicate unknown/error states. Absent tools are not displayed. Instructions/files have explicit export actions instead of misleading skill-installation indicators. Select a row to inspect source metadata, local paths, shared-folder occurrences and differing `SKILL.md` copies. Local name matches do not prove identical content or provenance; ambiguous source identities are not silently merged. Project-local skill scanning, cross-tool copying and uninstalling are not included.

Local discovery works without GitHub authorization. Repository listing reads metadata at an immutable commit independently of installation planning; repository failures do not hide local inventory. Missing/invalid `hub-manifest.json` produces one catalog-level error, not per-skill incompatibility warnings. Valid unlisted skills remain reviewable in Other. No tool allowlists, commit pins, whole-repository coverage or legacy approval fallback are required in the catalog. Local scans do not follow symbolic links/reparse points; unreadable or unsafe locations are reported instead of silently treated as absent. See [`docs/HubManifest.md`](../../docs/HubManifest.md) for the authoring schema and starter example; these must be published separately to the HMY repository.

The browser opens directly with padded Installed / HMY / Other view buttons. A compact theme-colored spinner beside the views indicates loading or an operation in progress, with details available to screen readers and on hover. A small Cancel icon appears during native operations; there is no separate loading row or Check again button. Reduced-motion preferences disable the spin animation. **Open GitHub repository** appears only in HMY, to the right of Category. GitHub sign-in is offered contextually in HMY rather than in a separate title/tool panel. Choose a repository skill and a target tool (or all compatible detected tools), then **Install skill**. Installation starts directly, without another tool-selection or confirmation step, and includes only the selected skill and its required dependencies from one immutable commit. Resource groups stay whole. Installation preserves local conflicts and continues other tools after a failure. Each tool has a separate recoverable transaction; the entire batch is not globally atomic. Catalog instructions and generic files use **Export…** with an explicit native Save As destination. Their original bytes are copied; they are never executed or automatically merged into user/project tool configuration. Destination edits detected before replacement abort the export; this does not isolate a same-user writer racing between filesystem calls. See the export guarantees in `docs/HubManifest.md`.

Successful installations show a compact **Installed in: …** message listing the affected tools, which disappears after five seconds. Failures, cancellations and preserved local conflicts remain visible as compact warnings instead of a persistent results panel.

Installing a single skill does not rescan the whole inventory. Only that skill and its required dependencies are refreshed, including copies observed through shared roots and existing copies in other tools. Unrelated inventory entries are retained unchanged; a full check still performs complete discovery.

Full discovery scans each distinct local root once and attributes shared occurrences to every observing tool. Repository skill metadata downloads use batches of at most six requests. Multi-tool preparation reuses immutable commit/tree/blob responses within that operation, keyed by credential, while access checks remain live. An existing session credential is verified before searching saved/environment/CLI credentials again. Initial loading still depends on repository latency and the number of local and repository skills; no persistent inventory cache is used.

The existing Copilot OAuth token is reused only after proving access to the private repository. Otherwise use the dedicated GitHub device flow; Copilot scopes and its saved token are never replaced. Tokens never cross the frontend bridge. Existing dedicated authorizations, `HMY_ESTAO_GITHUB_TOKEN`, and optional `gh` authorization are also supported. Payload integrity and reviewed-installation safeguards described in `docs/HarnessInstaller.md` still apply independently of catalog curation.

New dedicated Harness Hub authorizations use GitHub App client ID `Iv23lilqu6xECmxSGO99`. Enable Device flow on the App and install it with Contents read-only access to the skills repository (Metadata read-only is included). The user must also have access to the repository. No client secret or private key is included in Desktop. This is user authorization, not account-free installation-token access; that alternative requires a trusted backend. Existing valid authorizations are preserved and may be reused rather than prompting again. Copilot continues to use its separate OAuth client.

The session and downloaded plans exist only while Settings is open. Cancel or close Settings to cancel work; safe rollback finishes before payload cleanup. Persistent authorization and installer state use the existing `harness-github` and `harness-installer` directories beside `config.json`. An interrupted transaction exposes an inline warning and **Recover** action without restoring a separate tools section. General Settings Save/Discard do not apply or undo Hub installations.

`dotnet test Hmy.Estao.slnx -c Release` covers the source contract, installer, and Hub session with mock GitHub responses and isolated profiles. `npm test --prefix src/Hmy.Estao.Desktop/Frontend` covers skill selection and dependencies. Tests do not need a real GitHub authorization; the existing real-source integration test remains explicitly opt-in.

On first load without `usageAlerts`, the first enabled provider with custom colors supplies the global rule. If none exists, the first other custom rule is used, then the original defaults (75% amber, 90% red, customization disabled). The rule is copied, not aliased to the old provider setting. Once saved, the explicit global rule is authoritative, including when disabled.

Automatic refresh can be disabled. Initial, manual, account-change, and settings-save refreshes still run. Daily pacing remains provider-specific and uses the existing once-per-day notification store.

NuGet and npm need access to the HMY Azure Artifacts feeds. Configure authentication outside this repository. Do not commit credentials to `NuGet.Config` or `.npmrc`.
